## 글자 인식(OCR)

### 실시간 체크에서 6.9%가 6.3%로 읽힘

**증상**
- 화면 공유로 에코를 실시간 인식할 때, 같은 에코인데도 `6.9%`가 `6.3%`로 바뀌어 보이는 순간이 있었습니다.
- 값이 프레임마다 흔들려서 점수도 같이 깜빡였습니다.

**원인**
- 실시간 체크는 화면을 계속 찍어서 매번 새로 인식합니다.
- 게임 화면의 효과나 압축 때문에 어떤 프레임에서는 `9`의 아래쪽이 흐려져 `3`처럼 읽혔습니다.
- 프레임 하나의 결과를 그대로 화면에 보여 주고 있어서, 한 번만 틀려도 바로 드러났습니다.

**해결** (`src/utils/statVote.js`)
- 줄마다 최근 5번의 인식 결과를 모아 **가장 많이 나온 값**을 보여 주도록 바꿨습니다(다수결).
- 같은 값이 3번 연속 나오면 그 값으로 **고정**해서, 이후 한두 프레임이 틀려도 흔들리지 않게 했습니다.
- 다른 에코로 넘어가면(메인 옵션이나 옵션 이름이 바뀌면) 기록을 비우고 새로 모읍니다.

**결과**
- 잘못 읽힌 프레임이 섞여도 화면 값이 바뀌지 않습니다.
- 다수결과 고정, 초기화 조건은 단위 테스트로 확인합니다.

### 화면 비율 · 해상도가 다르면 인식 위치가 어긋남

**증상**
- 1920×1080보다 작은 스크린샷은 아예 거절됐습니다.
- 21:9 같은 넓은 화면이나 4K 스크린샷에서는 글자를 잘못 읽었습니다.

**원인**
- 인식 영역 좌표가 1920×1080 기준인데, 이미지를 단순히 잘라 맞추고 있었습니다.
- 게임은 화면이 넓어져도 UI를 높이 기준으로 키우고 스탯 창을 오른쪽 끝에 붙입니다. 가운데를 기준으로 자르면 스탯 위치가 어긋났습니다.
- 4K 이미지를 한 번에 줄이면 글자가 뭉개졌습니다.

**해결** (`src/utils/image.js`)
- 높이를 1080에 맞춘 뒤 **오른쪽 끝을 기준으로** 1920 너비만 남기도록 바꿨습니다.
- 큰 이미지는 절반씩 단계적으로 줄인 뒤 마지막에 맞춥니다.
- 작은 해상도도 거절하지 않고 같은 방식으로 맞춥니다.

**결과**
- 비율과 해상도가 달라도 같은 위치에서 스탯을 읽습니다.

### 11.6%가 1.6%로 읽힘

**증상**
- `11.6%` 같은 값이 `1.6%`로 인식됐습니다.

**원인**
- 게임 글꼴의 `1`은 획이 얇아서, 앞에 붙은 `1`이 하나 사라지는 경우가 있었습니다.
- 인식한 값을 실제로 나올 수 있는 옵션 수치 목록에 맞추는 단계가 있는데, `1.6`은 목록에 없어서 버려졌습니다.

**해결** (`src/utils/ocr.js`의 `snapSubStatsToCatalog`)
- 읽은 값이 목록에 정확히 없으면, 앞에 `1`을 붙인 값(`1.6` → `11.6`)이 목록에 있는지 한 번 더 확인합니다.
- 있으면 그 값으로 맞춥니다.

**결과**
- 앞자리 `1`이 빠져도 올바른 값으로 복원됩니다.
- 실제로 틀렸던 사례를 그대로 테스트로 남겼습니다(`src/utils/ocrSnapLeadingOne.test.js`).

### 인식 중에 다른 창으로 넘어가면 끝나지 않음

**증상**
- 에코 체크에서 "읽는 중" 상태일 때 게임 창으로 넘어가면, 사이트로 돌아올 때까지 인식이 끝나지 않았습니다.
- 사용자는 게임을 보면서 쓰기 때문에, 사실상 기능이 멈춘 것처럼 보였습니다.

**원인**
- 화면을 잘라 글자 인식기에 넘길 때 `canvas.toBlob()`으로 이미지를 만듭니다.
- 브라우저는 뒤에 숨은 탭의 작업을 미루는데, `toBlob()`의 콜백도 탭이 다시 보일 때까지 호출되지 않았습니다.
- 콜백을 기다리는 Promise가 끝나지 않으니 인식 전체가 멈춰 있었습니다.

**해결** (`src/utils/image.js`의 `canvasToBlob`)
- 탭이 숨겨져 있으면 바로 끝나는 `toDataURL()`로 이미지를 만들어 Blob으로 바꿉니다.
- 보이는 상태에서도 `toBlob()`이 0.5초 안에 응답하지 않으면 같은 방식으로 넘어갑니다.
- 인식 한 번에 15초 제한을 두어, 어떤 이유로든 멈추면 실패로 끝내고 다음 인식을 이어 갑니다.

**결과**
- 게임 창을 보고 있는 동안에도 인식이 계속 돌아갑니다.

### 이미 낀 에코를 다른 자리에 추천함

**증상**
- 에코 5번에 낀 에코를 그대로 인식시켰더니, "에코 4번 자리에 넣으면 점수가 오른다"며 추천 표시가 붙었습니다.
- 게임에서는 같은 에코를 두 자리에 동시에 낄 수 없습니다.

**원인**
- 인식한 에코를 각 자리와 비교할 때 "이 에코가 이미 낀 에코와 같은가"를 확인하지 않았습니다.
- 화면에 보이는 정보만으로는 같은 에코인지, 옵션이 똑같은 다른 에코인지 확실히 구분할 방법이 없습니다.

**해결** (`src/utils/echoIdentity.js`)
- 코스트, 메인 옵션, 서브 옵션(이름과 수치, 순서 무관)이 전부 같으면 **같은 에코일 가능성이 높다고 보고 알려만 줍니다.**
- 막지는 않습니다. 정말 옵션이 똑같은 다른 에코일 수도 있어서, 비교와 저장은 그대로 할 수 있습니다.
- 같은 에코로 보이면 추천 표시를 빼고, 해당 자리에 안내와 표시를 붙입니다. 다른 캐릭터 목록에서도 "착용 중인 에코와 같음"으로 보여 주고 교체 이득 순위에서 뺍니다.

**결과**
- 이미 낀 에코를 다른 자리로 옮기라는 추천이 사라졌습니다.
- 인식이 한 글자라도 틀리면 같은 에코로 알아보지 못하는 한계는 남아 있습니다.

### HDR을 켜면 인식되지 않는다는 제보

**증상**
- 사용자 제보: HDR을 켠 상태에서는 스크린샷과 화면 공유 모두 인식되지 않았습니다.

**원인(추정)**
- 인식은 글자와 배경의 밝기 차이를 기준으로 하는데, HDR 화면을 일반(SDR) 이미지로 캡처하면 색과 밝기가 달라집니다.
- 직접 재현은 아직 하지 못했습니다.

**대응**
- 스크린샷 주의사항, 화면 공유 주의사항, "인식이 잘 안되나요?" 안내에 HDR을 끄라는 문구를 추가했습니다.

## 화면 속도 · 체감

Cloudflare Web Analytics의 Core Web Vitals(실제 방문자 기준 체감 속도 지표)를 보면서 하나씩 고쳤습니다.

### 첫 화면의 큰 배너가 늦게 뜸(LCP)

**증상**
- 첫 화면에서 가장 큰 요소인 메인 배너가 늦게 떠서 LCP(가장 큰 요소가 그려지기까지 걸린 시간)가 나빴습니다.

**원인**
- 배너 주소는 서버 API가 알려 주는데, 그 API는 JS 파일을 다 받고 앱이 뜬 뒤에야 불렀습니다.
- 즉 HTML → JS → API → 이미지 순서로 줄을 서서, 이미지는 맨 마지막에 받기 시작했습니다.
- 배너 이미지 한 장이 350~380KB로 컸습니다.

**해결**
- 첫 배너 이미지로 바로 보내 주는 주소(`/api/banners/first-image`, 302 리다이렉트)를 만들었습니다(`MainBannerController.java`).
- `index.html`이 JS를 기다리지 않고 이 주소를 미리 받기 시작합니다(`preload`). 전에 와 본 사용자는 저장해 둔 첫 배너 주소를 바로 씁니다.
- nginx가 이 302 응답도 1분간 캐시해서 앱 서버까지 가지 않게 했습니다.
- 첫 슬라이드는 배너 목록을 기다리지 않고 바로 그립니다(`VersionBanner.jsx`).
- 관리자 화면에서 배너를 올릴 때 긴 변 1440px, WebP 품질 0.78로 줄이도록 했습니다.

**결과**
- 배너 용량: 380KB → 151KB, 352KB → 140KB.
- Cloudflare 기준 페이지 로드가 약 900ms로, 이전 24시간보다 16% 줄었습니다.

### 불러오는 동안 화면이 밀림(CLS)

**증상**
- 배너, 픽업, 방송 이미지가 뜨는 순간 아래 내용이 한꺼번에 밀려 내려갔습니다.
- 캐릭터 목록에서 필터를 누르면 목록이 줄면서 페이지 높이가 바뀌어 버튼 위치가 움직였습니다.
- 캐릭터 고르기 창이 검색 결과에 따라 커졌다 작아졌습니다.

**원인**
- 이미지 크기를 모르는 상태로 자리를 비워 두었다가, 다 받은 뒤에야 높이가 정해졌습니다.
- 목록과 창 높이가 내용 수에 따라 바뀌었습니다.

**해결**
- 이미지가 들어갈 자리는 비율(`aspect-ratio: 16/9`)과 `width`/`height` 속성으로 미리 잡고, 불러오는 동안 같은 크기의 자리 표시를 둡니다.
- 캐릭터 목록은 한 번 커진 높이를 줄이지 않습니다(필터로 목록이 줄어도 높이 유지).
- 캐릭터 고르기 창은 높이를 고정했습니다.

**결과**
- 불러오는 동안과 필터를 바꿀 때 화면이 밀리지 않습니다.
- 로컬에서 Puppeteer(브라우저 자동 조작 도구)로 페이지마다 레이아웃 이동을 측정해 확인했습니다.

### 메뉴를 눌러도 반응이 늦음(INP)

**증상**
- 무거운 화면으로 이동할 때 버튼을 누른 뒤 한참 있다가 반응했습니다.
- 스크린샷 여러 장을 인식하는 동안에는 화면이 굳었습니다.

**원인**
- 화면 전환이 끝날 때까지 브라우저가 클릭 반응을 그리지 못했습니다.
- 여러 장을 인식하는 반복문이 쉬지 않고 돌아 화면을 그릴 틈이 없었습니다.

**해결**
- 화면 이동을 React의 `startTransition`(급하지 않은 갱신으로 표시)으로 감싸, 클릭 반응을 먼저 그리게 했습니다(`App.jsx`).
- 인식 반복문이 사진 한 장마다 한 번씩 쉬어 가도록 했습니다.

**결과**
- 버튼을 누르면 바로 눌린 표시가 나고, 인식 중에도 진행률이 부드럽게 올라갑니다.

---

### 캐릭터 고르기 창이 느림

**증상**
- 캐릭터 고르기 창을 열면 캐릭터 사진이 하나씩 늦게 채워졌습니다.

**원인**
- 작은 칸에 보여 주면서도 원본 캐릭터 이미지(48장, 총 6.1MB)를 그대로 받고 있었습니다.

**해결** (`scripts/prepare-character-thumbs.mjs`)
- 캐릭터마다 128px 썸네일을 만들어 목록에서는 썸네일을 씁니다.
- 화면에 보이는 칸만 받도록 했고(`loading="lazy"`), 썸네일이 없으면 원본으로 대신 보여 줍니다.

**결과**
- 목록 이미지 총량: 6.1MB → 392KB.

## 검색 노출

### 검색 결과에 사이트가 한 줄로만, 이름 없이 뜸

**증상**
- 구글 검색 결과에 제목이 "Echo Setting Check"로, 설명은 화면 글자가 뒤섞인 채로, 아이콘 없이 떴습니다.
- 어떤 기능을 검색해도 홈 화면 한 줄로만 잡혔습니다.

**원인**
- `index.html`에 설명 태그, 아이콘, 사이트 이름 정보가 없었습니다.
- 모든 화면이 주소 `/` 하나에서 바뀌는 구조라, 검색 엔진에게는 페이지가 하나뿐이었습니다.
- 화면을 JS로 그리기 때문에, JS를 실행하지 않는 봇은 제목과 설명조차 화면별로 볼 수 없었습니다.

**해결**
- 제목, 설명, 아이콘, 링크 미리보기 정보(`og:`), 사이트 이름(구조화 데이터)을 넣었습니다.
- 화면마다 주소를 나눴습니다(`/build`, `/live-check`, `/echo-bag`, `/help` 등, `src/config/routes.js`).
  - 화면이 바뀌면 주소, 탭 제목, 설명이 같이 바뀌고 브라우저 뒤로 가기도 동작합니다.
- 빌드할 때 화면별로 제목과 설명만 바꾼 HTML을 따로 만들고, nginx가 해당 주소에 그 파일을 내줍니다(`vite.config.js`).
- `robots.txt`와 `sitemap.xml`을 추가했습니다.

**결과**
- 검색 엔진과 링크 미리보기가 화면마다 다른 제목과 설명을 읽습니다.
- 브라우저 뒤로 가기가 사이트를 나가지 않고 이전 화면으로 돌아갑니다.

## 서버 · 인프라

### Redis가 재시작되면 최대 10분간 다시 붙지 못함

**증상**
- Redis 컨테이너가 재시작된 뒤, 앱 서버가 한동안 Redis에 다시 연결하지 못했습니다.

**원인**
- 컨테이너는 재시작하면 새 IP를 받습니다.
- Redis 클라이언트(Lettuce)는 자체 DNS 캐시를 쓰는데, Docker DNS가 주는 유효 시간(600초) 동안 예전 IP를 계속 썼습니다.
- 그래서 Redis가 새 IP로 살아나도 최대 10분간 예전 IP로만 재접속을 시도했습니다.

**해결** (`RedisClientConfig.java`)
- Lettuce가 JVM 기본 주소 확인기(캐시 30초)를 쓰도록 바꿔, 재접속할 때 이름을 새로 확인하게 했습니다.

**결과**
- Redis가 재시작돼도 금방 다시 연결됩니다.

---

### 앱 서버가 재시작되면 nginx가 502를 냄

**증상**
- 앱 컨테이너가 재시작된 뒤, nginx를 재시작하기 전까지 API가 `502 Bad Gateway`를 냈습니다.

**원인**
- nginx는 `proxy_pass`에 적힌 이름(`app`)을 시작할 때 한 번만 IP로 바꾸고 계속 씁니다.
- 앱 컨테이너가 새 IP를 받아도 nginx는 예전 IP로 요청을 보냈습니다.

**해결** (`nginx.conf`)
- Docker 내부 DNS를 `resolver`로 지정하고 주소를 변수로 넘겨, 요청할 때마다 이름을 확인하게 했습니다(결과는 10초 캐시).

**결과**
- 앱만 재시작해도 nginx가 새 IP를 따라갑니다.

### Redis · DB가 죽으면 사이트 전체가 멈춤

**증상**
- 게임 데이터(캐릭터, 무기, 에코 목록)를 내주는 `/api/catalog`는 모든 화면이 처음에 부르는 API입니다.
- Redis나 DB에 문제가 생기면 사이트 전체가 동작하지 않을 수 있었습니다.
- Redis가 죽었을 때 Redis를 두 번 시도하느라 응답이 더 늦어지는 문제도 있었습니다.

**해결** (`CatalogService.java`)
- 읽는 순서를 **Redis → DB → 로컬 JSON 파일**로 두었습니다.
  - Redis가 죽으면 Redis는 한 번만 시도하고 바로 DB에서 읽습니다.
  - DB까지 죽으면 마지막으로 정상 갱신했을 때 저장해 둔 JSON 파일로 응답합니다.
  - JSON 파일은 임시 파일에 쓴 뒤 한 번에 바꿔치기해서, 쓰다 만 파일이 읽히지 않게 했습니다.
- 셋 다 실패하면 `503`과 "점검 중" 안내를 내고, 화면에는 로딩 표시와 안내를 띄웁니다.
- nginx도 앱이 응답하지 못하면 마지막으로 받은 응답을 대신 내줍니다(`proxy_cache_use_stale`).

**결과**
- Redis나 DB 하나가 죽어도 사이트는 계속 동작합니다.
- "Redis가 죽으면 한 번만 시도하고 DB 결과를 준다" 같은 상황을 단위 테스트(mock)로 확인합니다.

### 게임 데이터 API가 초당 190건에서 밀림

**증상**
- 부하 테스트에서 `/api/catalog`가 초당 약 190건부터 응답이 밀렸습니다.

**원인**
- 모든 사용자가 같은 응답을 받는 API인데, 요청마다 앱 서버(Spring)를 거치고 있었습니다.

**해결** (`nginx.conf`)
- 공개 API 응답을 nginx가 1분간 들고 있다가 그대로 내주도록 캐시했습니다.
- 캐시가 비었을 때 몰린 요청은 하나만 앱으로 보내고, 나머지는 그 결과를 기다리게 했습니다(`proxy_cache_lock`).
- 응답을 압축된 채로 캐시해서, 요청마다 다시 압축하지 않게 했습니다.

**결과**
- 같은 조건(nginx CPU 0.5)에서 초당 500건을 1ms 안에 응답했습니다.
- 앱 서버는 주소마다 1분에 한 번만 요청을 받습니다.

### Cloudflare 뒤에서 요청 제한이 사용자 여럿에게 한꺼번에 걸림

**증상**
- nginx에 IP당 초당 5회 요청 제한을 걸었는데, 정상 사용자들이 `429 Too Many Requests`를 받을 수 있는 구조였습니다.

**원인**
- 운영은 Cloudflare를 거쳐 들어오기 때문에, nginx가 보는 접속 IP는 사용자가 아니라 **Cloudflare 서버의 IP**입니다.
- 그래서 같은 Cloudflare 서버를 거친 여러 사용자가 한 사람으로 취급되어, 제한을 함께 나눠 쓰게 됩니다.

**해결** (`nginx.conf`)
- Cloudflare 대역에서 온 요청만 `CF-Connecting-IP` 헤더(진짜 사용자 IP)를 접속 IP로 쓰도록 설정했습니다(`set_real_ip_from`, `real_ip_header`).
- 다른 곳에서 온 요청은 이 헤더를 무시해서, 헤더를 위조해 제한을 피하는 것도 막았습니다.

**결과**
- 요청 제한이 사용자마다 따로 걸립니다.

### 봇이 찌르는 비밀 파일 주소에 200 OK가 찍힘

**증상**
- Cloudflare 로그에 `/client.ovpn`, `/grafana.ini`, `/config/secrets.yaml` 같은 요청이 1초에 수십 건씩 찍혔고, 대부분 `200 OK`였습니다.

**원인**
- 해외 봇이 흔히 쓰이는 설정 파일 이름을 돌아가며 요청하는 탐색입니다.
- nginx가 없는 주소를 전부 사이트 첫 화면(`index.html`)으로 돌려주고 있었습니다(SPA fallback).
- 실제 파일이 새어 나간 것은 아니고 첫 화면 HTML이 나간 것이지만, 로그만 보면 성공한 것처럼 보였습니다.

**해결** (`nginx.conf`)
- 사이트 HTML은 실제로 있는 화면 주소에서만 내주고, 나머지 없는 파일은 `404`로 끝내도록 바꿨습니다.
  - 처음에는 `/`와 소셜 로그인 복귀 주소(`/auth/...`)뿐이었고, 화면별 주소를 만든 뒤에는 그 목록(`/build`, `/live-check` 등)만 추가로 열었습니다.
- 점(`.`)으로 시작하는 경로(`.env`, `.git` 등)는 기존처럼 `403`으로 막습니다.

**결과**

| 요청 | 전 | 후 |
|---|---|---|
| `/`, `/auth/callback?token=…`, `/live-check` 같은 화면 주소 | 200 | 200 |
| `/client.ovpn`, `/etc/dovecot/…` | 200 (첫 화면) | 404 |
| `/.env` | 403 | 403 |
| `/characters/xxx.webp` | 200 | 200 |

### 게임 공식 이미지가 git에 계속 올라감

**증상**
- 관리자 페이지에서 캐릭터, 무기, 배너, 이벤트 이미지를 올릴 때마다 공식 이미지가 git 저장소에 쌓였습니다.

**원인**
- 이미지가 `public/` 아래에 저장되고, 배포는 git 코드로 Docker 이미지를 만드는 방식이었습니다.
- 그래서 이미지가 git에 있어야만 운영 서버에 올라갔습니다.

**해결**
- 공식 이미지 폴더 7개를 `.gitignore`에 넣고 git 추적을 끊었습니다(내 PC 파일은 그대로).
- 운영 서버에는 git 밖 폴더를 따로 두고, nginx 컨테이너에 그 폴더를 연결(volume)해서 같은 주소로 내보냅니다.
  - 폴더 위치는 서버 `.env`의 `CONTENT_IMAGES_DIR`로 정하고, 로컬에서는 기본값인 `../public`을 그대로 씁니다.
- 게임 데이터를 운영 DB에 덮어쓰는 스크립트가 이미지도 같이 서버에 복사하도록 했습니다.
  - 게임 데이터는 로컬이 원본이라, DB와 이미지를 명령 하나로 함께 반영합니다.

**결과**
- 공식 이미지가 더 이상 git에 올라가지 않습니다.
- 이미지 주소와 캐시 설정(30일)은 그대로라 화면 코드는 바꾸지 않았고, 속도 차이도 없습니다.
- 배포용 Docker 이미지가 이미지 파일만큼 가벼워졌습니다.
- 단, 이전 커밋 기록에 있던 이미지는 남아 있습니다.

## 장애 대응 순서

외부 모니터링(UptimeRobot)이 사이트 주소와 `/api/catalog`를 5분마다 확인하고, 응답이 없으면 알림을 보냅니다.
알림이 오면 아래 순서로 확인합니다.

1. **서버에 SSH로 접속되는지 확인**
   - 접속이 안 되면 서버 자체가 멈춘 것이므로 클라우드 콘솔에서 재부팅합니다.
   - 컨테이너는 `restart: unless-stopped`라 재부팅 후 자동으로 다시 뜹니다.
2. **컨테이너 상태 확인**
   - `docker compose ps`로 꺼졌거나 재시작을 반복하는 컨테이너를 찾습니다.
   - `docker compose logs --tail 100 app`으로 원인을 봅니다.
   - 우선 살려야 하면 `docker compose up -d`.
3. **디스크 · 메모리 확인**
   - `df -h`, `free -m`.
   - 디스크가 찼으면 `docker system prune`으로 쓰지 않는 이미지를 지웁니다.
4. **트래픽 때문이면**
   - Cloudflare의 Under Attack 모드를 잠시 켜서 봇을 거릅니다.

**평소에 해 둔 대비**
- 컨테이너마다 메모리 상한을 둬서, 하나가 메모리를 다 써도 그 컨테이너만 재시작됩니다.
- 공개 API 응답은 nginx가 1분간 캐시하고, 앱 서버가 죽어도 마지막 응답으로 계속 내줍니다.
- 계산과 글자 인식은 브라우저에서 돌아가서, 사용자가 늘어도 서버 부담이 크게 늘지 않습니다.
